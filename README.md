# Desert Frontline

Desert Frontline is an iOS SpriteKit RTS prototype inspired by the gameplay shape of Desert Stormfront and the provided reference screenshot. It does not reuse original game art; all map tiles, units, buildings, HUD elements, fog, and effects are generated with SpriteKit shapes.

- Tactical HUD visual system: a dark glass command console with a Blue Command resource strip, gold mission card and progress rail, cyan tactical map / selection cards, compact force-status readout, and a dedicated bottom command dock. The five single-row pages retain large, separated touch targets, page/action state highlighting, and existing command semantics while making the battlefield the visual focus.

## Current Features

- iOS SwiftUI app shell with a full-screen SpriteKit scene that resizes to the live window and uses a black launch fallback behind the game view.
- Isometric desert map matching the reference's desert RTS layout: deterministic warm sand color variation with sparse wind-cut dune contours and ripples; connected roads with dark shoulders, inset road beds, and direction-aware lane marks; ridges with varied rock silhouettes, cast shadows, lit facets, rubble, and sparse dark reef-edge fragments beside water; sand tiles with true water neighbors may also receive deterministic sparse short tide marks and tiny drift pebbles; oil fields with seep rings, surface cracks, and muted wet-sand lips beside water; coastline, deep water, shallow coastal water, layered shoreline wash and foam, sparse open-water wave marks, and directional layered bow wash / foam wakes on moving naval units, base clusters, desert villages, oases, farms, depots, wreckage, and fog of war. Land-side wet-sand, tide, pebble, and reef details are deterministic map decoration only and do not change terrain, collision, pathing, landing, or construction rules.
- Economy loop: HQ base income, capturable oil derricks, front-line flag control points with income, scout vision, limited build coverage, and one-time capture bonuses, visible money/income HUD, and AI income scaling by difficulty.
- Production queues from War Factory, Airfield, Shipyard, and Carrier decks with selected/least-busy source routing, land unit button subtitles that show the current `WF` source or `need WF`, `HELI` / `JET` button subtitles that show the current `AF` / `CV` source or `need AF/CV`, `SHIP` / `SUB` / `CV` subtitles that show the current `SY` source or `need SY`, visible factory progress bars, factory/carrier rally points with pending source summaries, and ready pulses on the map.
- Base construction from the HUD: place War Factory, Airfield, Radar Outpost, Sonar Buoy, Guard Tower, SAM Site, Coastal Battery, Shipyard, and Oil Derricks during play with a green/red placement preview, timed construction scaffolds, and visible build progress.
- Building rules: structures require vision and nearby friendly operational structure or captured flag build coverage; Shipyards, Sonar Buoys, and Coastal Batteries require coast tiles; Oil Derricks require oil fields.
- Shipyards use a compact static SpriteKit dock read with two short inset dry-dock rails, three low keel supports, a narrow inner quay edge, and three small mooring markers; these details stay inside the existing dock/crane visual envelope and do not change footprint, collision, construction, or production behavior.
- New structures are attackable while under construction but do not produce units, earn income, provide vision, provide support assets, extend base coverage, or fire weapons until operational.
- Radar Outposts are buildable land structures that provide extended static scout vision and count as `SCAN` assets once operational.
- Sonar Buoys are low-cost, fragile coastal detector structures that provide limited static vision and wide sonar detection once operational; they do not attack, produce units, earn income, or count as `SCAN` assets.
- Guard Towers are buildable land defense structures that automatically fire on visible land, air, and structure targets once operational; they do not attack naval units or submarines and do not provide sonar.
- SAM Sites are buildable land anti-air structures that automatically fire on visible air targets once operational; they do not attack land, naval, submarine, or structure targets and do not provide sonar.
- Coastal Batteries are buildable coastal defense structures with a layered concrete gun bed, revetment and sandbags, command bunker, ammunition crates, turret ring, shielded twin naval guns, breeches, rangefinder, and faction-lit optics. Once operational they automatically fire on visible surface naval targets; they do not attack submarines and do not provide sonar.

Visible surface-ship hits combine a main and secondary water column with a compact hull flash and sparks. Artillery retains its single water impact, and every attack cycle still applies damage once.

## Controls

Single-unit selection cards use a compact role tag (`LAND`, `AIR`, `SEA`, `SUB`, or `BASE`) before the unit name, so land, air, surface naval, submarine, and structure roles are immediately visible while reading HP and combat rows.
The same role tag uses a stable presentation color: sand green for land, sky blue for air, cyan for surface naval, violet for submarine, and sand gold for structures; incoming-threat red still takes priority.

The battlefield HUD puts resources in a narrow top strip, page navigation on the left, and only current-page actions in the bottom dock. The mission and message slots sit beside the rail; selection facts and the queue share one container above the dock. The upper-right minimap has separate legend, clickable content, and 44pt zoom bands. The large coin, duplicate theater card, and decorative LIVE labels are removed. Real window safe-area changes rebuild the same frames used for drawing and touch routing; two-finger pan/pinch keeps priority over HUD commands.

- Tap `TACT`, `BUILD`, `AIR`, `SEA`, or `SUP` in the left rail to switch the bottom action dock: tactical orders and HQ focus; land production and structure placement; aircraft production; naval production; or support powers plus AI difficulty and skirmish restart.
- Command-bar hit areas are isolated from the visual shapes: tapping a page/action frame invokes only that existing command, while the row's gaps are consumed without changing pending modes or touching the map.
- Tap a player unit to select it.
- Double-tap a player mobile unit to select visible units of the same type in the current camera view.
- Player selection uses a 26pt screen-scale minimum touch radius. Repeated taps in the same crowded friendly cluster cycle its living units in stable distance order and show `SEL i/n CODE`; a precise entity always takes priority, then a nearby player-known enemy that at least one selected operational combat unit can attack uses the same 26pt minimum radius without cycling, and only then can friendly assist selection run. Double-tap keeps the existing visible same-type selection.
- Drag on the battlefield to box-select mobile player units.
- Tap `G1` or `G2` to recall a saved control group of live player mobile units.
- Double-tap `G1` or `G2` to save the current player mobile-unit selection to that group; empty or structure-only selections do not overwrite an existing group.
- Control groups store unit IDs only, and dead or removed units are filtered when a group is recalled.
- Tap ground with units selected to move in formation; a short cyan-green `MOVE` reticle confirms each domain anchor, and if the order releases bound Carrier guard aircraft, the success message reports how many left `CV GUARD` with `Hn` / `Jn` composition.
- While units remain selected, a matching command intent line stays drawn from each unit to its current move, attack-move, attack, or HOLD intent so the player can read active orders after the short reticle fades.
- Tap a visible enemy with combat units selected to attack; a red dashed footprint-aware target ring with an amber double-chevron cue and `ATK <unit>` label confirms that at least one attacker was assigned. A near miss within the 26pt screen-scale minimum radius selects the closest player-known attackable enemy in stable distance / ID order and shows `ATK TAP <unit>` with the same target cue; it never cycles or bypasses a precisely hit entity. If assigned aircraft leave a Carrier guard wing for that attack, the success message reports the release count with `Hn` / `Jn` composition.
- Tap `HOLD` with mobile units selected to make them guard their current positions and return if pulled too far away; the button subtitle shows `CV GW` before holding selected Carriers and `CV rel` before ordinary HOLD would release selected bound guard aircraft. When a selected Carrier holds, up to two nearest nearby friendly operational Helicopters/Fighters are also assigned to hold as its guard wing with top-message `Guard wing n Hn/Jn` composition feedback, `Need n` when the final wing is short, and short deck-cue `Hn` / `Jn` feedback when aircraft are actually bound, bound to that Carrier for the compact `GW` HUD count, kept on stable nearby guard stations, reported as `CV GUARD` with anchor distance and an anchor Carrier guard-radius ring when those aircraft are selected, with the HOLD Carrier also showing its own guard-radius ring even before any aircraft are bound, and biased toward known attackable threats near that Carrier while it remains holding until they receive a new move, attack-move, attack, or ordinary hold order. Successful ordinary hold orders also report how many previously bound aircraft left `CV GUARD` with `Hn` / `Jn` composition when they are not immediately rebound to a Carrier.
- Tap `STOP` to clear current move, path, attack, attack-move, HOLD, and Carrier guard-anchor intent from selected live player mobile units without losing the selection. ## Development Workflow

Future Codex / programming-agent work should start from `AGENTS.md`, then read `update_log.md`, `md/flow/flow.md`, `md/flow/flowchart.md`, and `md/test/test.md`.

The project now uses an Agent A/B/C iteration loop:

- Agent A writes versioned implementation prompts under `md/prompt/`.
- Agent B implements on `main`, runs local lightweight checks, commits, and pushes to `origin/main`.
- GitHub Actions runs the cloud validation workflow and uploads an unencrypted CI results package.
- Agent C downloads the latest `main` results package, checks the manifest, JUnit summary, Xcode build log, and failure summary, then either accepts the run or returns a fix list to Agent B.

For larger goals, `agentx:` (`x:` / `X:`) starts the Agent X control loop. Agent X splits the goal into smaller Agent A -> Agent B -> Agent C rounds and decides whether to continue, return for fixes, pause, or finish after Agent C artifact review; it does not replace the A/B/C roles.

Feature changes must update this README with current behavior. Test or verification changes must update both this README and `md/test/test.md`.
