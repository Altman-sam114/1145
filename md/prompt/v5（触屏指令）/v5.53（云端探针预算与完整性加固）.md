## 4. 目标与有限实现方案

### 4.1 阶段可观测与统一预算

1. 将目前长内联模拟器 shell 适度提取到 `ci/` 的单用途脚本，或在现有脚本上收口，避免建设通用任务平台、矩阵或额外依赖。
2. 记录 generic build、simulator SDK build、设备选择、boot/bootstatus、install、prewarm、24 次正式探针、诊断和 cleanup 的阶段开始、结束、耗时、退出状态；输出 `probe i/24` 与名称。等待期间保留至少每 30 秒的可见心跳，预热 sleep 也不能成为长时间无输出黑箱。
3. 建议模拟器总工作预算 1080 秒，收尾诊断预算至多 90 秒，step 外层 21 分钟，job 仍 45 分钟；B 可按实现调整，但必须明确给出 `正常工作预算 + 有界收尾 < step 硬限时`，并为 metadata 3 分钟及 upload 5 分钟留出 job 余量。不得只增大外层 timeout 而不添加内层总 deadline。
4. 所有阶段和重试共享 monotonic 总 deadline；单命令限时不得超过剩余工作预算。保留 generic build 600 秒、模拟器 build 420 秒、bootstatus 每次 240 秒最多 2 次、launch 120 秒、screenshot I/O 180 秒、其他 simctl 60 秒的单项上限；`sips` 等图片后处理也必须有界。剩余预算不足时明确停止并写失败原因，而不是开始必然撞硬超时的重试。
5. 允许先选择并启动唯一一个云端模拟器，让其 boot 与模拟器 SDK 编译有限重叠，编译结束后再等待 bootstatus；后台进程必须有所有权、有界 wait 和退出清理。不要同时启动多个设备，不要把多个重任务盲目并发作为加速承诺。若难以安全实现，优先保留顺序流程并准确报告未做性能加速。
6. 保留首次成功预热后的 90 秒通知消退和正式截图原等待时间，不能靠删除通知防护、少等渲染或减少探针伪造提速。记录实际耗时，但单次 hosted runner 波动不能证明性能回归或长期改善。

### 4.2 明确的云端 runtime 选择

1. 在云端记录 Xcode 版本、可用且已安装的 iOS runtimes、所选 runtime 名称/版本/标识及 device 名称/UDID；不下载 runtime，不改本机环境。
2. 替换未说明的 `devices[0]` 选择为可解释、可重复的排序/偏好策略。只能选择 Xcode 支持、满足 app deployment target 的已安装可用 iOS runtime 和 iPhone；如有经过现有环境证据支持的稳定 runtime 可明确优先，否则 deterministic fallback 并在报告记录理由。不能把“旧版本一定快”当事实。
3. 不需要新建云端设备；同一 run 所有重试与 24 探针必须始终使用同一所选设备。无法匹配时快速失败并留证，不无限尝试、不在探针中切设备。

### 4.3 24 探针单一清单与完整性门槛

1. 用一个权威清单保存当前 24 个 probe 的名称、HUD page、command marker、camera focus、等待秒数和输出 PNG 路径，避免 launch 列表、report 和 manifest 三份手写映射漂移。保持现有全部文件名、场景、顺序和 24 次独立正式 launch；prewarm 单独统计。
2. 在每个阶段/探针完成后原子写 `simulator-probe-summary.json`（命名可调整并同步全部引用）：版本/run/attempt/commit、所选设备/runtime、总预算与耗时、当前阶段、最后完成 probe、每 probe 状态/PID/截图后存活、耗时、文件大小/尺寸/SHA-256，以及预期/完成/失败/未运行数量。
3. 探针成功至少要求：launch 返回合法且活跃 PID、原等待完成、截图命令成功、PNG 存在且非空且格式/尺寸合法、横屏规范化有界完成、截图后 PID 仍活跃。缺失、重复 probe ID/path、空图/错误 PNG、PID 已退出、超时均不得记 success。PID 及图像结构不证明画面正确，目视仍由 C 负责。
4. 最终校验必须证明权威清单 24 项一一完成、24 个预期 PNG 均有效、24 次正式 launch/PID 记录匹配，才允许 `simulatorLaunchOutcome=success`。失败保留已完成项和未运行项，不生成替代 PNG、不复制旧图凑数、不将 skipped 当 success。
5. 将结构化 summary 纳入 manifest/projectSpecificReports 和 artifact，failure summary 指出失败阶段及最后完成 probe。JUnit tests/failures/skipped 与实际 testcase 对齐；独立 XCTest 仍准确 skipped。

### 4.4 失败与取消留证

1. 正常、命令失败、总预算耗尽、SIGTERM/SIGINT 路径都应在 finally/trap 尽力写 summary，采集有界 simulator app log / device state，再对本 run 所有后台进程和唯一云端设备做有限清理。
2. 确保嵌套 watchdog/后台进程不会因各自新建 session 而逃脱取消；不得杀无关进程或全局 shutdown all。cleanup 错误不能覆盖原始失败状态或把失败转绿。
3. metadata/upload 继续 `always()`，即使探针脚本未能完整输出 summary 也应生成失败摘要与真实 outcome。runner 强制销毁或 GitHub 强制取消可能无法上传，文档必须保留该限制。

### 必须由 GitHub Actions 执行

- 保留 cloud-only watchdog 的成功、非零退出、超时和后代清理回归；增加取消/信号清理或总 deadline 传播的负路径证据。
- 为探针调度/summary/完整性校验加入小规模标准库测试或可注入 fake command 测试，不需要另一个 Simulator。覆盖 24 正常结果、缺一项、重复 ID/path、坏 PNG/空文件、PID 死亡、命令超时、剩余预算耗尽、失败后 summary 留存。运行日志需明确用例数与结果；失败进入静态检查/专门 test outcome 的最终门槛。
- 保留 generic iOS device build、真实 simulator SDK build、唯一云端设备预热、全部 24 正式 launch/截图/PID 检查和 artifact 上传。
- 本轮测试只验证 CI 调度/失败处理与固定 capture，禁止把它宣称为 gameplay、真实触控、多尺寸或长时间性能全覆盖。
