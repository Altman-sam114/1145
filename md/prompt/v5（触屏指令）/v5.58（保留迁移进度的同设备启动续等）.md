## 固定实施步骤

### 1. 单次初始boot与明确分类

1. 用局部启动入口替换现有 `for attempt ... boot/shutdown/reboot`，不要改设备选择。先仅在云端单次cap10s保存 `simctl help bootstatus` 原文及真实CLI回执，确认不带自动boot选项时是纯monitor语义；例如明确说明 `-b` 才会对未boot设备执行boot。不要要求整段help字符串逐字相等，只接受所需选项说明支持的明确语义；不支持/不清楚/非零/回执不完整则fail closed。正式两次等待一律使用不带 `-b` 或其他自动boot选项的 `simctl bootstatus <same UDID>`，防止state快照后状态变化时隐式再boot。该help也扣同一deadline，不在本机运行。
2. 整个启动阶段最多发一次初始 `simctl boot <selected UDID>`、最多两个纯监控bootstatus；两次bootstatus之间不发shutdown/boot/reboot，不清空App/设备/服务。现有finally只shutdown所选设备的收尾仍保留。本轮启动续等计数不包含成功启动之后、v5.56已有安装恢复的那次60s bootstatus；不得借安装恢复做第三次启动续等。
3. 初始boot保存真实命令回执/输出。正常exit0且回执完整才进入第一次bootstatus；唯一允许的非零入口是明确“当前状态已Booted”的既有CLI诊断，例如完整的 `Unable to boot device in current state: Booted`，仍须真实正常退出且CLI回执完整，并由bootstatus实际确认ready。正退出码的数值大小不能替代receipt的trigger/returnCode判断，不把已确认正常退出且有精确Booted诊断的命令错误标成信号取消；也不凭任意包含boot/booted的字符串或任意非零当alreadyBooted。不存在设备、unavailable runtime、参数/权限等永久错误、未知诊断、实际取消/信号或回收不明均停止。
4. bootstatus成功必须为真实正常exit0、trigger=exit、returnCode=0且回执完整。OS state=Booted、包含Finished的旧文字、计时器或仅PID不替代该成功。第二次任何非成功立即结束，不进行第三次或兜底重启。

### 2. 仅首个已确认超时允许有条件续等

5. 首次bootstatus只有实际返回124、receipt.trigger=timeout、完整TERM/KILL/reap无错误，才有资格评估续等；正常CLI自己exit124不能等同watchdog超时。保留EPERM/unreaped/error等真实结果，不改标already_gone、不吞错、不放松 `cli_receipt_complete`。取消/信号包括receipt显示cancelled、exception立即上抛，不能先做state查询或续等。
6. 分类同时读取这一次真实输出：永久错误优先拒绝；最后完整bootstatus状态须是已确认的非terminal Data Migration（如Status=2）或System App（如Status=4）等待，且相应等待文本一致。只记录从输出提取的lastStatus/isTerminal/reason/migration elapsed，不凭环境/早先一段“Waiting”覆盖末尾未知或失败状态；空输出、无法识别、terminal非成功、未知错误全部停止。无需声称OS迁移仍持续，只能记录“首个CLI最后观察到的等待”。
7. 若分类合格且预算允许，只做一次有界只读状态查询：复用已支持的 `simctl list devices --json`，仅从选定runtime条目中解析当前UDID，必须恰好一个、isAvailable=true、state=Booted；核对runtime/UDID/dataPath未变。保留原始JSON输出及所选条目，不扫描容器，不选择/操作其他设备。正常exit0、回执完整、JSON完整且身份/状态满足才继续；Shutdown/Booting/缺项/重复/跨设备/状态读取124/损坏JSON均保留失败，不能自动boot或拿最初available-devices快照冒充新状态。
8. 状态读取是一次轻量快照而非轮询，requested cap10s（不超过既有默认60s），实际cap同样受后续安装保留约束。该选项仅使用已有受支持list命令，不新增本机help或设备调用；若hosted在10s内无法读取状态，诚实失败，不循环查询/加长cap补救。它会增加实际开销，不能在报告中隐藏。

### 3. 与既有安装准入衔接，绝不延长总预算

9. 从既有常量/权威24 wait计算完整安装起点保留：`180 install + 2 CLI收尾 + 95 prewarm/settle + 100全部wait + 180后续命令余量 = 557s`。不修改安装的557/617准入或180命令余量，不因历史成功安装38.339s把install保留降至实测均值。
10. 每次启动bootstatus前重新读取共享monotonic剩余R，实际允许cap至多 `min(240, R - 557 - 2)`；单次help与一次state查询各至多 `min(10, R - 557 - 2)`。初始boot不超过既有60s且也留下557+2。这末尾2s是本次CLI已有收尾保留，与557内的安装CLI收尾不是同一份。cap非正或没有可发命令余量时不发命令，保存budget_insufficient；不重置deadline、不把续等另设240s总额、不引入额外sleep。
11. 状态读取完成后必须再用实际剩余重新算第二次cap，不能用读取前的R、首轮准入或手工拼出的剩余值。requested上限与真正传给run_bounded的effective limit都记录；与已有command层2s留量协调，不能无意双减2s或只在JSON中写保留却实际跑满240s。正常成功后仍由原 `_install_admission` 再验557s；调度/收尾超出预留就按真实剩余失败，不补时间或伪称保留得到保证。
12. 保持后续安装、launch help、prewarm90s通知与5ssettle、原24独立launch/8s或4s最小等待、正式30s就绪窗口、scene/snapshot/前5页hash、HUD25九类/producer/恢复、PID/raw270/final完整性及现有失败早停完全不变。启动续等成功不意味着后续必能完整完成，更不意味HUD视觉通过。

### 4. 小型boot证据与独立gate

13. 在现有summary加入版本化boot对象（建议schema1、policy `same-device-boot-continuation-v1`），绑定本run/SHA/attempt/version及选定UDID/runtime。记录单次help/确认的monitor语义、初始boot、1至2个bootstatus attempt、仅需要时的一个stateRead、各次预算准入和最终status/stopReason；不要建通用任务编排框架。每次包含实际argv、开始/结束monotonic相对时间、elapsed、remaining、requested/effective cap、reserve=557与CLI cleanup reserve=2、exit/status、真实process receipt、分类/continuationDecision。

15. 新增局部 `validate_boot...` 供runner最终gate和metadata各自调用，metadata在安装/HUD/scene失败时也独立给出真实boot结论。复核身份、次数/顺序、help输出的所需语义与正式argv确实无自动boot选项、初始boot成功或精确alreadyBooted理由、第一/第二bootstatus正常exit0或唯一允许的超时续等链、实际receipt、输出hash、fresh选定设备Booted状态、剩余/cap/保留与时序自洽；中间shutdown/reboot、跨设备、缺失/篡改/失败或未经确认的续等不能被完整HUD/PNG或summary总绿覆盖。
16. manifest新增 `simulatorBootOutcome`，失败摘要列boot最后阶段、实际等待/状态读取耗时、分类/续等决定、剩余/动态cap与stopReason；原始输出列入projectSpecificReports。建议JUnit新增simulator-boot，正常10case含1个准确skipped XCTest，以实际节点同步计数。不能因API continue-on-error step conclusion绿色忽略真实outcome，不能把启动未执行后的scene/HUD红说成scene断言失败。
